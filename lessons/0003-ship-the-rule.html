03 · Wire the rule into a project

TL;DR — A rule becomes useful when configuration loads its plugin and enables its name. Rebuild the rule from memory, then run its checks in CI.

Trace the wiring

The plugin exports meta.name = "lab" and the rule key no-focused-tests. Configuration loads ./plugin.js and enables lab/no-focused-tests. Paths resolve relative to the configuration file. Read Oxlint plugin registration.

{
  "categories": {
    "correctness": "off"
  },
  "jsPlugins": [
    "./plugin.js"
  ],
  "rules": {
    "lab/no-focused-tests": "error"
  }
}

Recall without copying

Close the solution. Implement exercises/no-focused-tests.js from memory, then run npm run exercise. It deliberately fails until you implement the rule. The solution tests remain separate, so a fresh clone has a passing CI suite.

Predict before revealing

Should test.only() trigger our enabled rule?

Decide what is safe to ship

Run npm test and npm run lint. Check .github/workflows/check.yml for the same commands. An automatic fix for .only changes which tests execute; our rule reports and asks you to decide.

Before using this in production

Review the false-positive and coverage limits from lesson 02. Prefer an existing framework rule when it already meets your needs. JS plugin APIs remain alpha, so the lab pins Oxlint 1.87.0. For a later optimization lesson, compare create with createOnce and learn how to reset file state.
